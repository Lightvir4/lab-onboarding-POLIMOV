# Практическое занятие 10

## 1 Матрица требований к серверной валидации

| Описание инцидента | Тип серверной проверки | Конкретное правило |
|---|---|---|
| Окончание бронирования раньше начала | Бизнес-логика; диапазон/формат | `end_date > start_date`; обе даты должны быть корректными ISO-датами |
| Заявка на -50 ноутбуков от пользователя -5 лет | Тип данных; диапазон/формат; бизнес-логика | `quantity` - целое число и `quantity > 0`; `age` - целое число в допустимом диапазоне, например 14-120 |
| Самоназначение `super_admin` в JSON | Авторизация/роли | Поле роли игнорируется в пользовательском запросе; изменение роли возможно только отдельным endpoint'ом с проверкой полномочий |
| Скрипт в комментарии | Безопасность/санитизация | Комментарий хранится как текст, а при выводе HTML экранируется; опасные теги и атрибуты удаляются санитайзером |

## 2 Чек-лист ревью API endpoint

- [ ] Все обязательные поля и их типы проверяются на сервере до выполнения бизнес-операции?
- [ ] Числовые значения ограничены допустимыми диапазонами и не допускают отрицательных значений, если это запрещено предметной областью?
- [ ] Связанные поля проходят проверку бизнес-инвариантов, включая `end_date > start_date`?
- [ ] Сервер определяет роль пользователя из проверенного контекста аутентификации, а не из тела запроса?
- [ ] Каждый endpoint проверяет авторизацию на чтение и изменение конкретного ресурса?
- [ ] Поля, отображаемые в HTML, экранируются или проходят утверждённую санитизацию?
- [ ] Ошибки валидации возвращают безопасные сообщения без внутренних деталей системы?
- [ ] Для отрицательных сценариев добавлены автоматические тесты, включая обход фронтенда прямым запросом?
- [ ] Изменение читаемо: правила вынесены в именованные валидаторы и не дублируются?

## 3 WSM для размещения основной валидации

Надёжность имеет максимальный вес: неправильные данные вредят бронированиям и ресурсам. Гибкость важна из-за меняющихся правил. Производительность и TCO учитываются, но не должны отменять гарантии целостности.

| Критерий | Вес | API Gateway | Application Layer | Database Constraints |
|---|---:|---:|---:|---:|
| Производительность | 0.20 | 5 | 4 | 4 |
| Гибкость правил | 0.30 | 3 | 5 | 2 |
| TCO | 0.15 | 3 | 4 | 3 |
| Надёжность при прямом доступе | 0.35 | 2 | 4 | 5 |
| **Итог Si** | **1.00** | **3.20** | **4.25** | **3.65** |

Расчёт для Application Layer: `0.20×4 + 0.30×5 + 0.15×4 + 0.35×4 = 4.25`.

Основная логика должна находиться в Application Layer: там удобно выражать сложные бизнес-правила и тестировать их. Оптимальная практическая комбинация: Gateway отсекает грубо некорректные запросы, Application Layer применяет предметные правила и авторизацию, Database Constraints защищают ключевые инварианты при прямом доступе.

## 4 Дополнения к Definition of Done

1. Для каждого изменённого API endpoint добавлены и проходят в CI тесты на серверную валидацию, авторизацию и негативные сценарии; фронтенд-валидация не считается доказательством корректности.
2. Pull request не может быть объединён без ревью по чек-листу безопасности и успешного автоматического анализа, который проверяет экранирование пользовательского ввода и отсутствие доверия к ролям из тела запроса.
